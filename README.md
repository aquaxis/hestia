# Hestia

[![CI](https://github.com/aquaxis/hestia/actions/workflows/ci.yml/badge.svg)](https://github.com/aquaxis/hestia/actions/workflows/ci.yml)

## Hardware Engineering Stack for Tool Integration and Automation

Hestia is an AI-driven hardware development environment that integrates FPGA, ASIC, PCB, HAL, and embedded software development tools. Nine Conductors (domain-specialized AI agents) collaborate via agent-cli IPC to enable automatic design generation from specifications, unified orchestration of vendor tools, and reproducible container-based builds.

[Workflow Reference](./WORKFLOWS.md)

## Features

- **9 Conductor Architecture** -- Domain-specialized AI agents for RTL, FPGA, ASIC, PCB, HAL, Apps, Debug, and RAG
- **Unified IPC** -- All inter-Conductor communication unified via agent-cli-compatible IPC (`agent-cli send <peer> <payload>`)
- **Engine Switching (Phase 113, Option C)** -- Select the peer-driven engine via `[engine] type = "agent_cli" | "claude_cli_shim"`. The latter is a `claude-cli-shim` wrapper that keeps Claude Code (`claude` CLI) as a child process
- **Specification-Driven Development** -- HDL code, constraint files, and testbenches are **dynamically generated by LLMs** from natural language specifications (template embedding is prohibited, Phase 42)
- **Vendor-Agnostic Abstraction** -- Unified interface via `ToolAdapter`/`VendorAdapter` traits. Add tools simply by writing an `adapter.toml`
- **Container & Local Execution** -- Choose between Podman rootless containers or local execution. Build reproducibility via lock files
- **AI Agent Pipeline** -- Automatic tool version tracking via WatcherAgent -> ProbeAgent -> PatcherAgent -> ValidatorAgent
- **Sub-Agent Concurrency Control (Phase 126)** -- 3-level hierarchical Semaphore + acquire timeout (global / ai-dispatch / per-conductor) to control spawn concurrency, with a reserved slot for reviewers to prevent starvation on critical paths. Configurable via `.hestia/config.toml` `[concurrency]`
- **Self-Update & Version Sync (Phase 124 / 127)** -- `hestia upgrade` rebuilds from source + installs to `~/.local/bin/`. `build.rs` uses `git describe` so `--version` display automatically syncs with GitHub tags

> **Hestia Design Principle**: Hestia is an AI-driven system. LLMs parse instructions and **dynamically generate HDL / constraints / TCL**, which handlers then process. An architecture that passes templates to handlers is prohibited (see [WORKFLOWS.md](./WORKFLOWS.md)).

## Quick Start

### One-Liner Install

```bash
curl -fsSL https://raw.githubusercontent.com/AQUAXIS/hestia/main/install.sh | sh
```

Install to a custom prefix:

```bash
curl -fsSL https://raw.githubusercontent.com/AQUAXIS/hestia/main/install.sh | sh -s -- --prefix ~/.local/bin
```

### Build from Source

```bash
git clone https://github.com/AQUAXIS/hestia.git
cd hestia/.hestia/tools
make build
make install PREFIX=~/.local/bin
```

### Project Initialization

```bash
hestia init          # Create .hestia/ directory structure
hestia start         # Start all Conductor daemons
hestia status        # Show daemon status
```

### Self-Update (Phase 124 / 130)

```bash
hestia upgrade            # git pull → cargo build --release (all binaries) → install 20 binaries to ~/.local/bin
hestia upgrade --no-pull  # Rebuild from current working tree only (skip pull)
hestia upgrade --dry-run  # Show install paths without executing commands
hestia --version          # e.g. "hestia 0.1.5-21-g1fe669f" (git describe sync via Phase 127)
```

As of Phase 130, `hestia upgrade` builds and installs **not just the `hestia` binary but all 20 binaries** (`hestia` / 9 conductors / 10 CLIs / `claude-cli-shim`). This means fixes on the conductor / library side (e.g., Phase 129 alive cap) are also applied with a single `hestia upgrade`.

`hestia --version` displays the version embedded by `build.rs` at build time using `git describe --tags --dirty=-dirty`. If the commit matches a tag, it shows `0.1.5`; if there are commits since the tag, it shows `0.1.5-21-g1fe669f[-dirty]`. For distributed binaries (environments without git), it falls back to `[workspace.package] version`.

## Requirements

- **Rust** 1.75+ (install via [rustup](https://rustup.rs))
- **Linux** x86_64 (kernel 5.x or later)
- **Engine (choose one, Phase 113)**:
  - `agent-cli` (default, drives inter-Conductor IPC via 4 backends)
  - `claude-cli-shim` + `claude` CLI + `ANTHROPIC_API_KEY` (Option C wrapper, uses Claude Code as the peer-driven engine)

### Engine Switching (Phase 113)

Select the peer-driven engine in the `[engine]` section of `.hestia/config.toml`:

```toml
[agent_cli]
backend = "claude"           # --provider inside agent-cli
model   = "claude-opus-4-7"

[engine]
# "agent_cli" (default, backward-compatible) | "claude_cli_shim"
type = "claude_cli_shim"
# binary = "/path/to/claude-cli-shim"   # Defaults to type default if omitted
# registry_path = "/custom/registry"    # Defaults to engine default if omitted
# log_path      = "/custom/logs"        # Defaults to engine default if omitted
```

- When `[engine]` is not configured, `agent-cli` is the default with full backward compatibility.
- When `claude_cli_shim` is selected, `~/.local/bin/claude-cli-shim` (or the path specified by `binary`) is used. The `claude` binary and `ANTHROPIC_API_KEY` are required.
- If sharing registry / log paths with agent-cli, be aware of peer name conflicts between the two engines (switching after `hestia kill` is recommended).
- For detailed specifications, see [`./report_claude.md`](./report_claude.md) (Phase 112 investigation report) and `.aiprj/AI_PRJ_DESIGN.md` sections 10-12.

### Sub-Agent Concurrency Control (Phase 126)

To prevent PC / LLM overload and deadlocks caused by too many sub-agents spawning, you can configure 3-level hierarchical concurrency limits in the `[concurrency]` section of `.hestia/config.toml`.

```toml
[concurrency]
global_max = 8                       # Total agents tracked by ai-conductor (HESTIA_GLOBAL_MAX_AGENTS)
ai_conductor_dispatch_max = 2        # Number of domain conductors ai-conductor dispatches simultaneously (HESTIA_AI_DISPATCH_MAX)
per_conductor_max = 4                # Max sub-agents each conductor can spawn simultaneously (HESTIA_PER_CONDUCTOR_MAX)
acquire_timeout_secs = 600           # Slot wait timeout in seconds (deadlock detection) (HESTIA_ACQUIRE_TIMEOUT_SECS)
```

- The hierarchical Semaphore enforces a **fixed L1 -> L2 -> L3 acquisition order** to eliminate circular wait.
- When `acquire_timeout_secs` elapses, **hold-and-wait is terminated** to detect deadlocks (a `dispatch_acquire_timeout` error is logged).
- One slot within `global_max` is **reserved for reviewers**, ensuring the auto-spawned ai-reviewer from Phase 77 can start even at the cap limit.
- Configuration priority (wiring added in Phase 128): **`hestia start` parent process env > `.hestia/config.toml [concurrency]` > library defaults**.
  - At `hestia start` startup, `[concurrency]` values are exported to child conductor process environments. **A `hestia kill && hestia start` restart is required** for `config.toml` values to take effect.
  - If `HESTIA_*` env vars are already set in the parent process, they take precedence over config.toml (useful for temporary overrides in tests / CI).
- The defaults (8 / 2 / 4 / 600s) assume a medium-scale workload. In environments with strict LLM rate limits, lower `global_max`; on powerful workstations, raise it.

> **Phase 131 alive cap semantics (enforced across all spawn paths)**: `per_conductor_max` is
> enforced as **"the absolute upper limit on the number of currently alive target sub-agents"**
> across **all paths** of `hestia spawn-subagent`. When a peer name has the format
> `<conductor>-<role>-<module>` (3 or more segments), `<conductor>-<role>-` is used as
> the cap prefix, the alive count is retrieved from the engine registry, and spawning
> is permitted only within the remaining `per_conductor_max - alive` slots.
>
> When the cap is reached, `spawn_agent_cli` will `bail!`, and the spawn is reliably
> refused across all of the following paths:
>
> - Via `rtl.dispatch_coders.v1` / `apps.dispatch_coders.v1` RPC
> - Via the path where a persona LLM directly calls `hestia spawn-subagent` (rtl.md / apps.md etc.)
> - Via manual `hestia spawn-subagent --persona X --name Y` CLI execution
>
> Example error message:
> ```
> alive cap exhausted: 1 >= 1 for prefix 'rtl-coder-'.
> Wait for existing sub-agent (rtl-coder-*) to complete or run hestia kill to consolidate.
> ```
>
> For concurrent `hestia spawn-subagent` calls, `~/.local/share/hestia/spawn.lock`
> (via `flock(2)`) serializes access to prevent TOCTOU races.
>
> Peer names with 2 or fewer segments (e.g., `pcb-layout`, `ai-reviewer`) are assumed
> to be single-instance and are not subject to the cap.
>
> Phase history:
> - Phase 126-128: Cap within a single dispatch call (bypassed across multiple calls)
> - Phase 129: Alive cap inside dispatch_coders.v1 handler (bypassed via persona)
> - **Phase 131**: Alive cap enforced across all spawn paths (completely seals bypass routes)

#### Minimum Sub-Agent Spawn Count

Each limit value has a `max(1)` lower-bound guard in the implementation (`ConductorLimiter::new` / `AgentManager::with_caps`), ensuring the following minimums.

| Setting | Minimum | Implementation Behavior |
|---------|---------|------------------------|
| `global_max` | **1** (1 slot for general spawn + 1 reserved reviewer slot, effectively 2) | `general = global_max.saturating_sub(1).max(1)` ensures the general limiter has at least 1 slot even with `global_max=0/1`. The reviewer reserved slot uses a separate Semaphore (capacity 1) always guaranteeing 1 slot |
| `ai_conductor_dispatch_max` | **1** | `Semaphore::new(max.max(1))` ensures at least 1 slot |
| `per_conductor_max` | **1** | Same as above |
| `acquire_timeout_secs` | Any value (1 second or more recommended) | Setting 0 causes immediate acquire timeout |

**Running with minimum settings**:

- With `HESTIA_GLOBAL_MAX_AGENTS=1 HESTIA_AI_DISPATCH_MAX=1 HESTIA_PER_CONDUCTOR_MAX=1`, execution becomes effectively sequential, minimizing PC / LLM load (1 general + 1 reviewer, max 2 sub-agents).
- Full sequential execution makes per-dispatch I/O behavior easier to debug, but overall throughput drops significantly. Useful in CI when you want to reproduce time-series behavior.

### Release Process (Phase 127)

`scripts/release.sh` atomically performs the `[workspace.package] version` update, commit, and tag.

```bash
./scripts/release.sh 0.1.6                  # Prepare release of version 0.1.6
git push origin main --follow-tags          # Push main + tag v0.1.6
```

The script performs: (1) update workspace version in `Cargo.toml` -> (2) regenerate `Cargo.lock` via `cargo build --release` -> (3) `git commit "Release vX.Y.Z" + git tag vX.Y.Z`. `build.rs` detects tag creation via `.git/refs/tags` watching, and the next build makes `hestia --version` follow the new tag. Push follows the safety protocol and is always manual.

## Design Principles

1. **Abstract, Don't Replace** -- Keep vendor tools as-is; orchestrate via unified interfaces
2. **Extend with Zero Changes** -- Add tools simply by writing an `adapter.toml`; no Rust code changes required
3. **Sustainable Maintenance** -- AI agents automate version upgrade handling
4. **Security** -- Container isolation via Podman rootless; API keys managed via environment variables
5. **Reproducibility** -- Complete build reproducibility via lock files
6. **Vendor Independence** -- OSS tools preferred; integrate any vendor tool via the plugin system
7. **AI Utilization** -- Specification-driven development; AI-assisted design process via Tool Use
8. **Unified Interface** -- All communication unified via agent-cli IPC
