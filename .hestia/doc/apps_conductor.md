# Application Software Development Orchestrator

**Target Domain**: apps-conductor
**Source**: Design specification §9 (lines 2281-2400)

---

## Overview

`apps-conductor` is a conductor that abstracts the development flow for application software (firmware / RTOS applications / bare-metal applications) running on target hardware. It integrates cross-compilers, RTOS, linker scripts, and HIL (Hardware-in-the-Loop) / SIL (Software-in-the-Loop) testing, building and verifying application logic using drivers generated by `hal-conductor`.

## AppsToolAdapter Trait

```rust
#[async_trait]
pub trait AppsToolAdapter: Send + Sync {
    fn id(&self) -> &str;
    fn target_arch(&self) -> &[TargetArch];     // arm-cortex-m / riscv32imac / xtensa-esp32
    fn supported_languages(&self) -> &[AppLanguage];  // C / C++ / Rust

    async fn build(&self, project: &AppProject) -> Result<Artifact, AdapterError>;
    async fn flash(&self, artifact: &Artifact, target: &Target) -> Result<(), AdapterError>;
    async fn test(&self, project: &AppProject, mode: TestMode) -> Result<TestReport, AdapterError>;
    async fn size_report(&self, artifact: &Artifact) -> Result<SizeReport, AdapterError>;
}
```

```
Idle → Resolving → Compiling → Linking → SizeChecking → Flashing → Testing → Done
                                       ↓ (memory exceeded / link error / test failed)
                                   Failed → Diagnosing → Fix suggestion
```

```toml
[rtos]

[memory]
flash_origin  = 0x08000000
flash_length  = "256K"
ram_origin    = 0x20000000
ram_length    = "64K"
linker_script = "memory.x"

[hal]
import = "build/hal/rust/soc-hal"       # Import output from hal-conductor

[test]
mode  = "hil"                           # "sil" | "hil" | "qemu"
probe = "stlink-v3"                     # Provided by debug-conductor
```

## Upstream and Downstream Integration

- **Upstream (hal-conductor)**: Import HAL modules (C headers / Rust crates / Python modules) generated by hal-conductor via `[hal] import = "..."`
- **Cross-cutting (debug-conductor)**: Perform flash writing / RTT logging / GDB sessions via debug-conductor
- **Testing**: Supports 3 modes: SIL mode (QEMU) / HIL mode (physical device + debug-conductor) / cross-testing (QEMU + cycle-accurate co-sim)
- **CI/CD**: Reproducible builds on GitHub Actions / GitLab CI via shared services layer / CI/CD API
- **ai-conductor integration**: ai-conductor supports automatic generation of apps.toml from application specifications (Spec-Driven)

## Public Methods

Five method groups: `apps.build.v1` / `apps.flash.v1` / `apps.test.v1` / `apps.size.v1` / `apps.debug.v1` (bridging with debug-conductor). Sent as structured JSON payloads over agent-cli IPC.

## Sub-Agent Configuration

apps-conductor has 5 types of sub-agents: **planner / designer / coder (multiple) / builder / tester**, and improves application development efficiency by dynamically assigning multiple coders in parallel per functional module. Each sub-agent is launched as an independent agent-cli process and coordinates with the apps-conductor main body (peer name `apps`) via `agent-cli send <peer>` IPC.

| Sub-Agent | Peer Name | Role | Multiplicity |
|----------------|---------|------|-------|
| **planner** | `apps-planner` | Application development planning (RTOS selection, memory layout, task partitioning, HAL import strategy) | 1 |
| **designer** | `apps-designer` | Application detailed specification (task structure, IPC protocol, state transitions, error handling policy) | 1 |
| **coder** | `apps-coder-{module}` | Application code (C / C++ / Rust) implementation per functional module | **N** (dynamically launched in parallel per module, capped by `per_conductor_max` default 4, Phase 126) |
| **builder** | `apps-builder` | Cross-compilation / linker script application / binary size optimization | 1 |
| **tester** | `apps-tester` | SIL (QEMU) / HIL (physical device + debug-conductor) / unit test execution + coverage aggregation | 1 |

**Flow**: Sequential execution in the order planner → designer → coder (parallel per module) → builder → tester. For large applications (module count >= 4), coders are dynamically expanded up to `per_conductor_max` entries (the former hardcoded 16 was replaced with env-driven configuration in Phase 126).

> **Phase 126 / 128 / 129 Concurrency Control**: `apps.dispatch_coders.v1` also controls
> concurrency via `conductor_sdk::concurrency::ConductorLimiter`, the same as rtl, and
> **in Phase 129, the semantics of `per_conductor_max` were switched to "alive cap"**.
>
> When dispatch_coders.v1 is called, `count_alive_peers_with_prefix("apps-coder-")`
> retrieves the current alive coder count, and `available = per_conductor_max - alive`
> calculates the remaining slots. When the alive cap is reached, 0 spawns are skipped
> with `status: "cap_exhausted"`.
>
> The upper limit can be changed via the environment variable `HESTIA_PER_CONDUCTOR_MAX`,
> and if `HESTIA_ACQUIRE_TIMEOUT_SECS` elapses, the corresponding coder is skipped due
> to acquire timeout.
> For details, see [`user_guide.md`](user_guide.md) §3.12.
